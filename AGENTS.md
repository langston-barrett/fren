# Issue labels

Set or change issue priority labels only at the user's explicit behest. Requests to triage issues or apply labels do not authorize setting or changing priority labels.

# Reviews by separate agents

Each author agent does one whole PR, from the first commit until it merges, then ends. New work goes to a new agent. Keep PRs small: one lint, one spec chapter or one fix per PR. Split larger work into a stack of PRs that each build and pass on their own. If the author finds a bug while writing the PR, it fixes the bug in that PR, with a test, rather than only filing an issue.

Each PR head gets a review from a fresh agent that has no earlier context, never from the author. The reviewer reads the full diff against the base and judges it skeptically, without trusting the PR body. When the change touches code or proofs, it relies on CI rather than building and testing itself, once the `pre-merge` workflow has run on the head: `gh pr checks <number>` shows its `pre-merge` check, which passes only if `lake build --wfail` and `lake test` (all but the mutants of Fren's own requirements, which CI checks on `main`) passed on the head merged into main. Check that the run is of the current head (`gh run list --workflow pre-merge --branch <branch> --json headSha,conclusion`), and treat a failed run as a blocking finding. A new front-end difference that `fren_fuzz_frontends` finds in a construct the PR touches is blocking too, as a failing test is, whether the corpus in `lake test` caught it or the reviewer's own fuzzing did. The reviewer may still build and run targeted probes, such as one test job, to check a suspicion. Where CI's binaries run, probe with them rather than building. `gh run list --workflow pre-merge --branch <branch> --json headSha,databaseId` gives the run of the head, and `gh run download <id> -n fren-<full head sha> -D /tmp/fren-<sha>` (or `-n fren_test-<full head sha>`) fetches the stripped binary that CI built from the head merged into main, with that merge commit's sha in `MERGE_SHA`. Probe in a checkout of exactly that commit (`git fetch origin <sha>`, then `git checkout --detach <sha>`), not of the head: once main has moved, the head's tests, specs and `.olean` files no longer match the binary. If GitHub no longer serves the commit, merge the head into main's commit as `MERGE_PARENTS` names them. `chmod +x` the binary if the download lost the executable bit. The artifacts are kept for 3 days. `fren_test`'s `ui`, `uiMisread`, `uiAskAgain`, `smtAgreement` and `leanTokens` jobs also need `scripts/heavy lake build Fren` in that checkout, then `scripts/heavy --offline lake env <dir>/fren_test --job ...`. Where they don't run, build as before. When CI hasn't run on the head, the reviewer builds and runs the tests itself. It posts one PR comment whose first line is exactly `Review of <full head sha>: no blocking issues` or `Review of <full head sha>: blocking issues`, followed by numbered findings, each marked [blocking] or [non-blocking]. Before writing a finding, the reviewer searches the diff and the files it touches for the same mistake, and the finding lists every other instance, by file and line, so that one push can fix them all.

The `pr-review` workflow does this review in CI. Once `pre-merge` passes on the head of an open PR that is not a draft and comes from one of this repository's own branches, it reviews that head by these rules, a full review or the light check the author asked for, and posts a comment with the same first line. That comment is the head's review for every purpose: its blocking findings, its light checks and the PR's readiness to merge, so no local review of that head is needed. A fresh local agent reviews the head only when no review of it is posted and none is pending: for example a PR from a fork, a draft, a PR opened by a bot, or a `pr-review` run that failed or posted only a note that starts "The `pr-review` workflow did not review", which counts as no review. A wording-only head (below) is the exception: it has no review and none pending, but the coordinator's comment confirming its diff and its skip stands in for one, so no local agent reviews it. A draft marked ready after its `pre-merge` passed gets no run until its next push, so rerun the workflow by hand (below) or push again. A failed run can instead be rerun by hand once `pre-merge` has passed on the head: `gh workflow run pr-review -f pr=<number> -f post=<number>`. Don't start a local review of a head while the workflow's review of it is pending, that is, while its `pre-merge` run is in progress or its `pr-review` run (`gh run list --workflow pr-review`) is queued or running.

When a review has blocking findings, or the PR conflicts with main, the PR's author handles it:

1. Fix every [blocking] finding, at every instance of its mistake: the ones the finding lists and any others in the diff. If you disagree with one, reply on the PR with your reasoning instead.
2. Reread the whole diff against main for anything else each finding's mistake touches, and fix it too.
3. Rebase onto main if needed, and run the checks.
4. Push with `--force-with-lease`, after confirming the PR is still open.
5. Post a comment that says what changed for each finding.

Before each push whose head will get a full review, the first push included, the author may run `scripts/local-review` once, where the Codex CLI is installed. It has Codex review the branch against main, read-only and off the web, with the brief that the `pr-review` workflow gives its reviewer, and prints what Codex finds. This pre-push check is not a review in the sense of this process: it never stands in for one, is never cited as one, and is never posted as a PR comment that starts "Review of". Fix only the findings that you have checked against the code yourself, and ignore the rest without arguing them. Skip it before rebase-only, fixes-only and wording-only pushes.

When a review finds a bug, the review says why the spec did or didn't catch it. Was the property stated at all? Was it stated but checked only by tests, or checked over a bounded domain? Was the spec too abstract, or did it take the deciding fact as a precomputed input? The fix then strengthens the spec so that it would catch the bug, or the author's comment explains why no reasonable spec could. Check a reported bug before fixing it: the review of #385 showed that a "bug" an author filed was the intended behaviour.

The new head then gets a fresh review. One exception: when the previous head's review was clean and the new head only rebases it, the author says so in a comment ("rebase only"), listing the resolutions. That head gets a light check instead of a full review. The checker reads `git range-diff <old base>..<old head> <new base>..<new head>`, confirms the patch is unchanged apart from the conflict resolutions, and judges those resolutions. It then checks that the `pre-merge` CI run of the new head passed, or, when CI hasn't run on it, runs `scripts/heavy lake build --wfail` and `scripts/heavy lake test`. It posts `Review of <full head sha>: no blocking issues (rebase only)` or `Review of <full head sha>: blocking issues`. Any change beyond the rebase gets a full review (a light check runs on a smaller model, so when it finds more changed than the request lists, it posts `blocking issues` with one finding saying the head needs a full review; the author or coordinator then posts a comment that names the head without asking for a light check and reruns the workflow by hand, as for a failed run), with one more exception: when the previous head's review was clean and the new head only fixes that review's non-blocking findings, the author says so in a comment ("fixes only"), listing what changed for each finding. That head gets a fix check: the checker reads `git diff <old head> <new head>` (or the range-diff, if it also rebases), confirms that each change answers a listed finding and that nothing else changed, and judges those changes. It checks CI as for a rebase check, and posts `Review of <full head sha>: no blocking issues (fixes only)` or `Review of <full head sha>: blocking issues`. A light check judges only what changed since the head it checks against, whose code had its review. In code that the diff from that head (or, for a rebase, the range-diff) shows unchanged, it raises only [blocking] findings: any other point about such code is [non-blocking], never "fix before merge", and goes as a checklist item on the area's queue rather than into the PR. The workflow and local checkers read a request for a light check the same way. A comment asks for one only if it is not itself a review, starts with "rebase only" or "fixes only" (in any case, after any leading Markdown emphasis, quoting or heading marks), names the new head by at least its first 7 hex digits, and is the latest such comment naming that head: a later comment that names the head without asking for a light check gets it a full review. The head it is checked against is the one reviewed last before the request, whose review must have been clean. Only comments by the repository's owner, members and collaborators count, as requests and as reviews. Post the request as soon as you push, since the workflow decides the kind of review when `pre-merge` passes; a request that comes later gets a full review.

A head that only fixes wording needs no check at all. When the previous head's review was clean and its only "fix before merge" findings are about prose, the author fixes them in one commit whose only parent is that reviewed head, with no rebase, and as soon as it pushes posts a comment that starts with "wording only:", names the new head by its full sha (at least its first 7 hex digits count, as for a light check), and lists the findings that the commit answers. Prose here is Markdown prose outside code blocks, the text of code comments and docstrings, and the PR description, apart from text that decides behaviour or process, such as the rule paragraphs of `src/Reqs`, the `--explain` texts in `src/FrenCore/Codes`, AGENTS.md and everything under `.github/`. Code, tests, workflow logic, a spec's code blocks, snapshots, generated files and such texts are not prose here, so a change to any of them gets a fix check instead. The comment is read by the same rules as a request for a light check: it counts only if it is the last comment by the repository's owner, members and collaborators that names the new head and is not a review, and the reviewed head is the one whose review was posted last before it, which must be clean. When `pre-merge` passes on the new head, the `pr-review` run that it starts checks that the new head's only parent is the reviewed head and that it changes neither AGENTS.md nor anything under `.github/`. If so, the run posts nothing, and its `prepare` job's log says "Nothing to review: wording only:" followed by the reviewed head; otherwise the run gives the new head a full review. The coordinator reads `git diff` from the reviewed head to the new one and confirms what a fix check would: that each change answers a "fix before merge" finding that the comment lists, that it changes only prose, and that nothing else changed. It also confirms that the new head's `pr-review` run (`gh run list --workflow pr-review`) succeeded and that its log has that "Nothing to review: wording only:" line, since every other skip prints "Nothing to review" too. It records both in a comment that also starts with "wording only:" and names the new head, so that this comment, now the last one naming the head, leaves the skip standing. Only then does it queue the merge, which happens once `pre-merge` and `lint` pass on the new head. If any of these checks fails and the run has not already given the new head a full review, the coordinator posts a comment that names the new head without starting with "wording only", so that the head gets a full review, and reruns the workflow by hand (above) to do it.

A PR is ready to merge when the review of its current head says no blocking issues, or, for a wording-only head, when the review of the head it fixes said so and the coordinator has posted its "wording only:" comment confirming the diff and the skip, as above. Don't merge a head whose review hasn't been posted, with that one exception. Start a review only once the head's `pre-merge` run has passed, and when a PR whose merge is queued gets a new head, take it out of the queue (`gh pr merge <number> --disable-auto`) until that head's review is posted, or, for a wording-only head, until the coordinator has posted that confirming comment. `main` requires the `pre-merge` and `lint` checks to pass on the PR's head, but not that the branch be up to date with `main`: `pre-merge` tests the head merged into `main` as it was when the run started. So the coordinator queues a ready PR with `gh pr merge <number> --squash --auto`, and GitHub merges it once both checks pass and the merge is clean. If it conflicts with `main`, the author rebases it, and the new head gets a rebase check if the author asks for one, as above, or else a full review. An update that only merges `main` into the branch (`gh pr update-branch <number>`) leaves the PR's own patch unchanged and needs no new review. Two PRs that merge cleanly can still break each other, so `main`'s own CI is the last check: when it fails, fixing or reverting the cause on `main` comes before any other merge. A check that fails because of a known flaky timeout is rerun on the same head, and that needs no new review. Fix the small non-blocking findings (wording, comments, a missing test, a small spec tightening) in the PR before it merges, in the same push as any blocking fix. When the review was clean, the author fixes them in one push that gets a fix check, or none if they are wording only (above), rather than leaving them for later. Only substantive non-blocking findings, which are real work in their own right, become a follow-up issue labelled `note/follow-up`, and only once per PR. Smaller leftovers go as a checklist item on the area's tracking issue ("Area: <name> — queue"), not as a new issue. A new finding that belongs to an existing umbrella issue, such as the one for front-end differences, goes on that issue. Every open issue is a sub-issue of exactly one area's tracking issue, in queue order. Issues should not pile up faster than they are resolved: when an area has more than 5 open follow-ups, its next author takes the most important of them into its PR alongside its new work. A PR is never only leftover fixes, apart from the fixer agent's. The fixer agent works only on these already-filed follow-up issues, one small PR each, and owns those PRs like any author.

# Saving build work across worktrees

Each worktree has its own `.lake`, and building one from scratch compiles every module and dependency. Seed a new worktree from one that is already built before you build it:

```sh
git worktree add <dir>/fren-<topic> -b <topic> origin/main
cp -R <a built worktree>/.lake <dir>/fren-<topic>/.lake
```

Copy-on-write copies, where the filesystem supports them, are fast and use almost no disk. Lake's traces survive the copy, so Lake rebuilds only the modules that differ.

Every worktree needs its own `.lake/packages`, never a symlink to another worktree's. Lake checks out each worktree's pinned lean-smt in its packages directory, so worktrees that share one fight over it: a branch that pins another revision checks it out under everyone else, and with an `insteadOf` rule for GitHub, Lake then reports "URL has changed", deletes the shared clone and clones it again. `cp -R` copies a symlink as a symlink, so check the source first, and seed from one whose `.lake/packages` is a directory, such as the main checkout's:

```sh
test -L <a built worktree>/.lake/packages && echo "symlink: seed from another worktree"
```

Reviewers and fixers reuse one worktree for each PR, checking out each new head, rather than adding a new worktree for each head. A built `.lake` takes about 2 GB, and the disk fills: when your PR merges, or you finish a review whose PR has merged, delete your worktree's `.lake` (`rm -rf <worktree>/.lake`), never another agent's. Lake's artifact cache is shared between worktrees on a machine, so deleting a `.lake` frees little: once a week, or when the disk is short, run `scripts/heavy python3 scripts/lake_cache.py prune`, and never `lake cache clean` while anything may be building.

`lake build` and `lake test` each use every core. Run them, and other all-core commands such as `lun run --check`, mutation runs and fuzzers, through `scripts/heavy`, for example `scripts/heavy lake test`. It waits for a free one of a few machine-wide slots, so parallel agents don't pile up, and keeps them under a memory cap (see `src/Reqs/dev/Testing.md#heavy-jobs` for the defaults and overrides). Run binaries that a PR built, fuzzers and mutation runs, which never need the network, through `scripts/heavy --offline`, so that they run with no network; it fails rather than run them online. Builds and `lake test` stay online, since Lake fetches packages and elan fetches toolchains. Other agents' commands run on the same machine, so stop only your own processes, by pid. Never use `pkill -f` or `killall` with a pattern such as `lake build`, which also matches theirs. While iterating, run only the affected tests. Before pushing, run `scripts/heavy lake build --wfail` and the test jobs your change affects; CI's `pre-merge` runs the full `lake test` on the PR, and its result is the gate.

To run one test job, build the driver with `lake build fren_test` — plain `lake build` does not build it, and a stale driver silently reproduces the results of whatever head it was built from — then run `scripts/heavy --offline lake env .lake/build/bin/fren_test --job NAME ARG...`, which prints the job's failures as JSON (`[]` if it passed). Examples: `--job ui test/ui/lints/names.fren` runs ui tests through both front ends; `--job snapshots`, `--job libraries` and `--job errorCodes` run those checks; `--job mutation 0 3 8` runs one slice of the mutants of Fren's own requirements. `lake build Reqs.Lint` (or any module) rebuilds just that module and what it imports.

# Keeping the front ends together

Both front ends must give the same messages for every spec. Two rules keep them so:

- A decision both front ends make, such as which guards bound a quantifier, which expressions are a count, which checks an item has, or what a pass rests on, is one function in `Fren.Core` that both call. It is bound to the Req that states it with an `impl`. Each front end only extracts that function's inputs from its own representation. A deciding fact is never handed to a Req as a precomputed input when the Req could compute it.
- A PR that changes how the front ends read or check a construct extends `fren_fuzz_frontends` to generate that construct in all its forms (every type, nesting, definition and comparison it can take). It then runs a few thousand specs, and fixes every difference the PR causes before pushing. Differences that predate the PR go to the issue that tracks them. `lake test` checks a fixed corpus of the fuzzer's seeds, so an extension must leave every existing seed's spec unchanged: make its random draws after all the existing ones, or from a generator of its own split off the seed. What it appends must not add an error, since an error stops every check of the spec: put deliberate errors in a mode or spec of their own. Never relist `knownDifferences` to absorb a changed corpus.

Avoid stacking a PR on another that is still under review: base it on main, or wait until the lower PR is close to merging.
